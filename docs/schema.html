Hyrabostad data model

PostgreSQL 16 with PostGIS, managed by Drizzle. One listing is one home; a sighting of that home in a source is a separate row, which is what makes freshness, removal and "listed by several sources" work.

  • 22 tables
  • 14 enums
  • Geometry in SRID 4326 (WGS 84), GiST-indexed
  • Schema at src/db/schema.ts

Geography where a home is

Real municipalities with SCB codes, slugs in both languages and a centroid. Areas are districts inside a municipality. Polygons are nullable columns waiting for Lantmäteriet data.

municipality

One row per kommun. Slugs differ per language so a language switch resolves the same entity.

  • code
  • name_sv
  • name_en
  • slug_sv
  • slug_en
  • county
  • centroid
  • geom

area

District such as Södermalm or Arenastaden; unique per municipality.

  • municipality_id
  • name
  • slug
  • centroid
  • geom

Landlords and sources who publishes, and how we read it

A landlord is any organisation we know of, monitored or not; that difference is what the coverage figure counts. A source is one way of reading a landlord: a feed, an API, a page, or the portal itself.

landlord

Known organisations. is_known and is_monitored drive "14 of 18 monitored".

  • org_number
  • slug
  • name
  • type: municipal | private | agency | foundation
  • queue_type
  • queue_info_url
  • website
  • approved_at

landlord_municipality

Where a landlord operates. Join table behind the coverage table.

  • landlord_id
  • municipality_id

source

One crawl target. Health fields are product data, shown in admin.

  • landlord_id
  • kind: feed | api | html | manual
  • adapter
  • url
  • config (field mapping, selectors, key)
  • status: pending | active | degraded | failed | disabled | needs_review
  • consent
  • queue_default
  • fetch_interval_minutes
  • next_run_at
  • consecutive_failures
  • tech_contact_email

source_run

One row per crawl: found, new, gone, error class, and whether the anomaly guard fired.

  • source_id
  • started_at
  • finished_at
  • ok
  • listings_found
  • listings_new
  • listings_gone

  • error_class
  • error_detail

Listings the home, its sightings, and its history

The canonical home lives in listing. Each source that shows it gets a listing_source row with the source's own id and the raw payload. Every tracked change becomes a revision, which powers the portal timeline.

listing

Canonical fields. Nullable rent, rooms and size: we never guess.

Scored pairs for staff review; merges point the loser at the survivor.

  • listing_a_id
  • listing_b_id
  • score
  • features
  • decision: pending | merged | not_duplicate | ignored
  • decided_by
last_checked_at is when we last read the source successfully, whether or not the home changed. last_seen_at is the last run where it was present. Absent on a successful run → removed, row kept forever. Failed run → nothing removed, source marked degraded.

Accounts and onboarding who may sign in, and to what

A landlord application is the review-queue row. Approval creates or attaches a landlord and gives the applicant an owner membership. Staff are ordinary users with a staff role. Every portal query is scoped by the member's landlord id.

landlord_application

Sign-up form plus automated checks as JSON, one status per stage.

  • org_number
  • company_name
  • website
  • contact_name
  • contact_email
  • publishing_route: source | manual
  • source_url
  • automated_checks
  • status: pending | needs_info | approved | rejected
  • user_id
  • landlord_id
  • reviewed_by
  • decision_note

landlord_application_event

Audit trail: submitted, needs_info with message, approved, rejected, reopened.

  • application_id
  • kind
  • message
  • actor_id

landlord_member

Workspace membership. Owner publishes and invites; editor drafts.

  • user_id
  • landlord_id
  • role: owner | editor

landlord_invitation

Hashed single-use token, 24-hour expiry.

  • landlord_id
  • email
  • role
  • token_hash
  • invited_by
  • expires_at
  • accepted_at

staff_user

Marks a user as staff. Sessions capped at eight hours by the guard.

  • user_id
  • role: support | lead | engineer

Not in the database on purpose

Saved homes and saved searches stay in the seeker's browser (a cookie and localStorage), so seekers have no accounts and no personal data here. Crawl jobs live in a separate pgboss schema in the same database.
