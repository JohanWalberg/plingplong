# Deploying to Render

`render.yaml` in the repository root is a Render Blueprint: one web service, one
background worker and one Postgres instance, all in **Frankfurt**, because the
data is Swedish rental listings and the personal data in it should stay in the
EU.

It validates against Render's published schema
(`https://render.com/schema/render.yaml.json`).

## Before the first deploy

**1. Create the object storage bucket.** Render's disk is ephemeral and belongs
to one instance, so uploaded listing photos cannot live on it. Any S3-compatible
bucket works; Cloudflare R2 is the cheapest fit. Keep the bucket **private** —
images are served through `/api/uploads`, never directly from the bucket. You
need the bucket name, either the region (AWS) or the endpoint (R2, MinIO), and a
key pair scoped to that bucket alone.

**2. Have a Resend API key and a verified sender domain.** The app refuses to
start in production without `RESEND_API_KEY`, deliberately: without it, password
reset links are written to the log.

**3. Decide the public origin.** `NEXT_PUBLIC_SITE_URL` is baked into the build,
so it decides canonicals, hreflang, the sitemap, share cards and whether cookies
get `Secure`. On the first deploy it is `https://hyrabostad.onrender.com`; when
you attach a custom domain, change it **and redeploy**, because a stale value
here fails quietly rather than loudly.

## Deploying

1. Push the repository to GitHub.
2. In Render: **New → Blueprint**, pick the repo. It reads `render.yaml`.
3. Render prompts for every value marked `sync: false`:

   | Variable | Value |
   |---|---|
   | `NEXT_PUBLIC_SITE_URL` | `https://hyrabostad.onrender.com` (or the custom domain) |
   | `BETTER_AUTH_URL` | the same origin |
   | `S3_BUCKET`, `S3_REGION` or `S3_ENDPOINT`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | from step 1 |
   | `RESEND_API_KEY`, `EMAIL_FROM` | from step 2 |
   | `SENTRY_DSN` | optional; errors are logged either way |

   `BETTER_AUTH_SECRET`, `REVALIDATE_SECRET` and `SOURCE_SECRET_KEY` are
   generated by Render and shared with the worker. Do not set them by hand.

4. Apply. The web service's **pre-deploy command** runs `pnpm db:migrate`, which
   creates the PostGIS extension and applies every migration before the new
   instance takes traffic, so the schema is never behind the code serving it.

Nothing seeds the production database. `pnpm db:seed` truncates every table and
creates users with a published password; it refuses to run against
`NODE_ENV=production` unless `ALLOW_SEED=1`, and there is no reason to override
that. Create the first staff user by hand.

## What the app checks at startup

`src/lib/env-check.ts` refuses to start in production if the configuration would
be quietly wrong. Each of these is a real failure mode, not a formality:

- `BETTER_AUTH_SECRET` shorter than 32 characters, or still a placeholder.
- `BETTER_AUTH_URL` that is not an `https://` origin — it decides `Secure`
  cookies and the origin check.
- Missing `RESEND_API_KEY`, which would send reset links to the log.
- `STORAGE_DRIVER` not chosen explicitly, because defaulting to local disk on a
  host that throws the disk away loses photos on the next deploy.
- Missing or unparseable `TRUSTED_PROXY_HOPS`. Every rate limit is keyed on the
  address it resolves; guessing wrong either lets one caller pose as thousands
  or collapses thousands into one bucket and locks everyone out. **On Render it
  is 1**, which the blueprint sets.

A failed check stops the deploy with the list of problems. That is the intended
behaviour: a half-configured deploy is worse than none.

## Scaling: one web instance for now

The rate limiter and the query memo cache live in the web process
(`src/lib/rate-limit.ts`, `src/lib/ttl-cache.ts`). With one instance that is
correct. With two, each keeps its own counters, so the effective sign-in limit
doubles and cached facets can disagree between instances for up to
`CACHE_TTL_SECONDS`.

Neither is dangerous, but **do not raise the web service above one instance**
until both stores are moved to Postgres or Redis. The worker is unaffected — it
is a singleton by design and pg-boss holds the queue in Postgres.

## After it is up

- `GET /api/health` returns 200 when the database answers; Render uses it as the
  health check.
- Set `CACHE_TTL_SECONDS` if you want the public search memo to last longer than
  the default 60 seconds.
- Watch the log for `[csp]` lines. The enforced policy is permissive about
  inline scripts; a second, stricter policy runs in report-only mode and reports
  to `/api/csp-report`, so those lines say what a move to nonces would have to
  answer first.
- Watch for `[sync] source … still offered after a staff takedown`, which means
  a landlord's feed keeps re-offering a home staff removed.

## Costs

`starter` for both services and `basic-1gb` for Postgres is the smallest
sensible shape. The worker is idle between crawls and can drop to the smallest
instance; the web service should not, because the Next build runs there.
