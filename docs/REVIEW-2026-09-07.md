# Code and security review, 7 September 2026

Scope: the whole repository at commit `ecd84ad`, read-only, in five passes (auth and access, input handling and data access, ingestion and outbound fetching, web platform and dependencies, code quality and tests). Every finding below was verified against the code; file and line references are to that commit.

Baseline: typecheck clean, 51 unit tests and 19 end-to-end tests pass, translation catalogues in parity (1114 keys), `pnpm audit` reports one moderate advisory in development tooling only.

## Verdict

The application is in good shape for a pre-launch codebase. Tenant scoping is consistent (no IDOR found), role checks are server-side everywhere, SQL is parameterised throughout, there is no `dangerouslySetInnerHTML`, no open redirects, no committed secrets, uploads are path-safe, and the public surface is well covered by axe. The weaknesses cluster in three places: **outbound fetching of landlord-supplied URLs** (server-side request forgery and no response size cap), **a gap in the invitation flow** combined with open self-registration, and **hardening that has not been done yet** (security headers, transactions, worker robustness, CI). None of it is exotic; all of it should be fixed before a public deploy.

Fixed during the review: memoized queries sharing a namespace collided on equal arguments, which hid the partial-coverage banner when caching was on (commit `ecd84ad`).

## Security findings

### S1. High. Server-side request forgery through source URLs

`src/worker/fetch.ts:43-52,68-84` is the single outbound fetch path and only does `new URL(url)`: no scheme restriction, no private-address check, redirects followed, ports unrestricted. It is reachable by an unauthenticated visitor through the application form (`src/actions/signup.ts:72-74`, where `sourceUrl` is not even `.url()`-validated), by any approved owner through the connection test (`src/actions/portal-sources.ts:26-46`, no rate limit), and hourly by the crawler for every stored source. The connection test echoes HTTP status, error class and a parsed sample back to the caller, and the crawler stores whole items as raw payload.

Impact: port scanning of internal services, reaching cloud metadata (`169.254.169.254`), and partial exfiltration of any JSON an internal service returns, since a response containing id and address-like keys is parsed as listings.

Fix, in `politeFetch` and the robots fetch: allow only `http:` and `https:`, ports 80 and 443, resolve the host with `dns.lookup({ all: true })` and reject loopback, private, link-local, unique-local and multicast ranges, use `redirect: "manual"` and re-validate each hop (cap five), and pin the connection to the validated address (undici `Agent` with a custom lookup) to close the DNS rebinding window. Validate `sourceUrl` on sign-up with `.url()`, rate-limit the connection test per user, and consider deferring the sign-up feed test to the approval step.

### S2. High. Invitation acceptance attaches a pre-existing account without proving ownership

`src/actions/invite.ts:69-70`: when a user row already exists for the invited address, the submitted name and password are ignored and the membership is granted to that row. Better Auth's public sign-up endpoint is open (`src/lib/auth.ts:19-28`, no `disableSignUp`), so anyone can pre-register a colleague's predictable work address with their own password. When the owner later invites that address and the colleague accepts, the membership, possibly `owner`, lands on the attacker's account. The colleague's auto sign-in fails and they are bounced to sign-in; if they reset the password, the attacker's session survives (S5).

Fix: when an existing user is found, require the caller to be signed in as that user, or verify the submitted password against the account with `auth.api.signInEmail`, before inserting the membership. Close the public sign-up route with a `hooks.before` on `/sign-up/email` that rejects HTTP calls while the two server-side `signUpEmail` calls keep working (verify `disableSignUp: true` does not block them before using that instead).

### S3. High. Feed-supplied and staff-entered URLs are rendered as links without a scheme check

`src/worker/normalise.ts:130,146` stores `raw.url` and `raw.image` as-is; `src/actions/admin.ts:317,347` stores `applicationUrl` as-is, and `admin.ts:130,133` `website` and `queueInfoUrl` likewise. They render as `href` on the public listing page (`home/[slug]/page.tsx:90,282,191`) and landlord page (`landlords/[slug]/page.tsx:118`), and as image `src` (`listing-image.tsx:38`, unoptimized passes the string through). React does not neutralise `javascript:` or `data:` in `href`. The manual portal form does check the scheme (`portal-listings.ts:63`); the crawler and admin paths do not. Feeds are third-party content under a landlord's control.

Fix: one `safeHttpUrl()` helper (parse with `new URL`, allow only `http:`/`https:`, cap length at 2000) applied in `normalise()`, `adminUpdateListing`, `upsertLandlord` and the sign-up `website`; resolve relative feed URLs against the source URL; and as a last line, have `OutboundLink` and the raw anchors drop links that do not start with `http`.

### S4. High. No HTTP security headers

`next.config.ts:19-26` sets only `X-Robots-Tag` on admin. There is no HSTS, CSP, `X-Content-Type-Options`, frame-ancestors, `Referrer-Policy` or `Permissions-Policy`, and `x-powered-by` is sent. Missing `nosniff` matters for `/api/uploads/*`, which serves user bytes; missing `Referrer-Policy` sends the full listing URL to every hotlinked landlord image host.

Fix: for `/(.*)` add `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=()`, and set `poweredByHeader: false`. Start a CSP in report-only mode: `default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob: https:; font-src 'self'; connect-src 'self' https://tiles.openfreemap.org; worker-src 'self' blob:; child-src blob:; frame-ancestors 'none'; base-uri 'self'; form-action 'self'; object-src 'none'; upgrade-insecure-requests`. Fonts are self-hosted by `next/font`, so no Google hosts are needed. A nonce-based script policy can come later for the dynamic portal and admin groups.

### S5. Medium. Password reset does not revoke existing sessions

`src/lib/auth.ts:19-28` omits `revokeSessionsOnPasswordReset`. A user resetting a password because they suspect compromise leaves the attacker's seven-day session valid. The in-app change-password path does revoke (`account-forms.tsx:147`). Fix: set `emailAndPassword.revokeSessionsOnPasswordReset: true`.

### S6. Medium. Rate limiting trusts a client-controlled header and is per process

`src/lib/rate-limit.ts:33-37` keys on the first `X-Forwarded-For` entry, which the client controls unless the proxy overwrites the header. This keys sign-up (5/h), metrics and suggest. Better Auth has no `advanced.ipAddress.trustedProxies`; behind two proxy hops it collapses every visitor into one shared sign-in bucket (a global lockout any client can trigger), and with no proxy a spoofed header gives a fresh bucket per request. Both stores are in memory per instance.

Fix: configure `trustedProxies` and `ipAddressHeaders` for the real hop chain, make `clientIp` take the right-most untrusted hop or the platform's canonical client-IP header, cap the number of keys in the store, and move both stores to Postgres or Redis before running more than one instance.

### S7. Medium. Metrics can be inflated for any listing

`src/app/api/metrics/route.ts`: listing ids are public, the only controls are a user-agent regex and a spoofable per-IP limit, every hit is a synchronous upsert, and there is no origin check. Landlord dashboards are trivially fakeable. Fix: dedupe per visitor per listing per day (hashed IP plus UA, or an anonymous cookie), require `status = 'active'`, cap increments per listing per day, reject requests whose `Sec-Fetch-Site` is not `same-origin`, and consider batching increments.

### S8. Medium. Uploaded image type is taken from the client

`src/actions/portal-listings.ts:125-127` trusts `f.type`; `sharp` is installed but never used to validate. Files are served with a one-year immutable cache and no `nosniff`. The extension is server-chosen so browsers will not execute the bytes, but any 8 MB blob can be stored as an image, there is no cap on images per listing, and EXIF location data in landlord photos is kept. Fix: decode with `sharp` and re-encode (rejects non-images, strips metadata), cap images per listing at about 12, add `nosniff`, and tighten the route key regex to the exact generated shape `^listings/[0-9a-f-]{36}/[0-9a-f]{16}\.(jpg|png|webp)$`. Note also that Next caps server action bodies at 1 MB by default and `next.config.ts` does not raise it, so the 8 MB limit is unreachable and multi-photo uploads over 1 MB fail today; set `serverActions.bodySizeLimit`.

### S9. Medium. Seed script has no production guard and a documented password

`src/db/seed.ts:32` defines the dev password, `:339` truncates every table, `:588-601` creates lead, support, engineer and landlord users with `emailVerified: true`. `reset.ts:6` refuses in production; `seed.ts` does not, and `db:push` is exposed in `package.json`. One accidental run against the production URL wipes data and creates a lead staff login with a public password. Fix: the same production guard as `reset.ts`, or an explicit `ALLOW_SEED=1`; drop `db:push`.

### S10. Medium. Worker: disabled sources re-activate, consent is never enforced

`src/actions/portal-sources.ts:109-118` lets an owner run a source that staff disabled, and `sync.ts:221` then flips it back to active on success. `source.consent` is written in four places and read nowhere, so a source marked `objected` still crawls. Fix: refuse disabled sources in `syncSource` unless a staff-only `force` flag is passed, never transition away from `disabled` on success, and skip `consent = 'objected'` in `dueSources` and `syncSource`.

### S11. Medium. The anomaly guard defeats itself after three runs

`sync.ts:52-58` builds the baseline from the last five `ok = true` runs, and `:217` records anomalous runs as `ok: true`. A feed that suddenly returns zero items is flagged three times, then the median drops to zero, the guard turns off, and every listing is removed, about three hours at the default interval. Fix: exclude runs with `anomaly = true` from the baseline, and stop scheduling `needs_review` sources until staff mark them reviewed.

### S12. Medium. Failure email goes to an unverified address with attacker-influenced content

`sync.ts:250-254` emails `techContactEmail`, which a landlord sets freely, with the source URL and the raw error message, and an owner can trigger it every few minutes by toggling the source. Fix: only allow member addresses or require verification, rate-limit `runSourceNow` and `setSourceEnabled`, and truncate the error before templating.

### S13. Medium. Sitemap advertises pages marked noindex

`src/app/sitemap.ts:22,27` lists `/map` and every `/homes/[place]`, both of which set `robots: { index: false }`. Search Console will report these as errors. Fix: drop them from the sitemap, or remove the noindex on the municipality search pages if they are meant as landing pages.

### S14. Low. Draft listing data leaks through the share image and saved page

`getListingBySlug` has no status filter; the page guards drafts but `home/[slug]/opengraph-image.tsx` renders address, rent and landlord for any slug, and a draft slug in the saved cookie renders a card. Slugs are deterministic from the address. Fix: filter drafts inside `getListingBySlug` and the saved-page query.

### S15. Low. Wildcards in search terms are not escaped

`queries/admin.ts:33,131,159`, `queries/portal.ts:55`, `queries/places.ts:109-127` interpolate user terms into `ILIKE` patterns (parameterised, so no injection), and the public suggest endpoint runs a correlated count per matching row, so `q=%%` evaluates every municipality and area. Fix: escape `%`, `_` and `\`, reject wildcard-only terms, consider a trigram index later.

### S16. Low. Scalar server-action arguments are only TypeScript-typed

`changeMemberRole`, `setStaffRole`, `decideDuplicate`, `setSourceStatus`, `requestMoreInfo`, `rejectApplication` and `adminRemoveListing` take roles, enums and free text without runtime parsing; the strings go into emails unbounded. All are behind role guards. Fix: a small zod schema at the top of each action.

### S17. Low. Client storage is trusted on read

`saved-searches.tsx:26` renders `href` from local storage without a shape check; `recent.ts:25` only checks the slug. Poisoning needs an existing same-origin script, so impact is small. Fix: on read, require `href` to start with `/` and not `//`, and `imageUrl` to be null or start with `/api/uploads/` or `https://`.

### S18. Low. Cookie and configuration hygiene

`hb_saved` and `NEXT_LOCALE` lack `Secure`. `BETTER_AUTH_SECRET` has a placeholder that passes Better Auth's check; `NEXT_PUBLIC_SITE_URL` and `BETTER_AUTH_URL` silently default to localhost, which produces localhost canonicals and cookies without `Secure` in production; `email.ts:12-13` prints full emails, including reset links, to stdout when `RESEND_API_KEY` is unset. Fix: `secure` on both cookies over https, and a startup assertion in production for the three variables.

### S19. Low. Miscellany

`findInvitation` is an exported server action returning the raw row (move to queries). Application form reveals whether an org number or email is taken. A crafted `?denied=1` link signs the visitor out. A user can belong to several landlords but the guard picks an arbitrary one. There is no way to remove a staff member. Unknown-slug share images echo the slug as a branded card. API keys are stored in plaintext in `source.config`. `robots.txt` crawl-delay is ignored and the robots fetch bypasses the host queue. Better Auth's five-minute cookie cache keeps a revoked session usable briefly.

### Dependencies. Info

`pnpm audit`: one moderate advisory, `esbuild <= 0.24.2` reached only through `drizzle-kit`'s loader (development tooling, not shipped). Fix with a `pnpm.overrides` for `esbuild >= 0.25` or wait for drizzle-kit. Runtime packages are current: Next 16.3.4, React 19.2.8, Better Auth 1.7.2, next-intl 4.14.2, Drizzle 0.45.2, zod 4.5.4, sharp 0.35.4, MapLibre 6.7.0.

## Code quality findings

### Q1. High. A listing is published before its images are validated

`src/actions/portal-listings.ts:186-211` inserts the row with `status: "active"` and invalidates caches before `saveImages` can return `invalidImage`. A bad photo leaves a live listing while the form shows an error. Fix: validate type and size from the `FormData` before any write.

### Q2. High. No transactions anywhere

`db.transaction` is used zero times. `approveApplication` (landlord, member, source, enqueue, application, event; no unique constraint on landlord plus URL, so a retry makes a second source), `mergeListings` (a crash between copying sources and marking the loser leaves an active listing with no sources), `closeLandlordAccount` (seven statements), plus `saveListing`, `adminRemoveListing`, `expireDirectListings`, `acceptInvitation` and `upsertLandlord` all need one.

### Q3. High. Sign-up leaves orphan users on partial failure

`src/actions/signup.ts:53-79` creates the Better Auth user first, then does network calls (registry lookup, feed test with a 30 s timeout) and two inserts. Any failure after the user exists leaves a user with no application, and a retry says the email is taken. Fix: create the user last or delete it in a catch, and queue the feed test.

### Q4. Medium. The sync loop is unguarded and the worker has no shutdown

Only the fetch is in a try/catch (`sync.ts:33-47`). A poison item (for example a floor of `99999999999`, which overflows Postgres integer) rejects the job with nothing logged, leaves the run row open, never advances `nextRunAt`, and the tick re-enqueues the same source every five minutes forever. There is no per-source item cap, so one huge feed blocks the single worker for hours, and no `SIGTERM` handler, so a deploy kills a sync mid-loop. Fix: clamp numerics and lengths in `normalise`, wrap the body in a try/catch routed to `recordFailure`, cap items per run, honour the abort signal, and add `boss.stop({ graceful: true })` on `SIGTERM`.

### Q5. Medium. Server-action error conventions are mixed

`admin.ts` returns `void`, `{ ok, error? }` and a discriminated union in different actions; some failure paths return `void` so the UI toasts success. Zod issue text (English only) is returned to the staff UI in three places, and `action-buttons.tsx:40-42,75-77` shows `e.message`, which Next redacts in production into a generic string. Fix: one `{ ok: true } | { ok: false; error: <key> }` shape, keys translated in the UI.

### Q6. Medium. Race conditions

Slug generation is select-then-insert in four places (unique constraints turn this into an exception rather than corruption, but in the worker that exception hits Q4). `decideDuplicate` checks `pending` without a lock while the worker may auto-merge the same pair. Fix: retry on unique violation, and `UPDATE ... WHERE decision = 'pending' RETURNING` as the guard.

### Q7. Medium. Per-row database work in the worker

A 500-item feed is roughly 1500 to 2500 round trips per run: per new listing a sibling lookup, up to 49 slug probes, an insert, a revision and a source link; per removal two or three statements. Batch revision and link inserts and resolve siblings and slugs in one query per run. `existing` also pulls full rows including geometry; select the tracked columns.

### Q8. Medium. Time zone leaks

`filter-panel.tsx:211` (move-in cutoff, browser UTC), `sync.ts:346` (expiry cutoff, UTC) and `admin.ts:8-9` (`setHours(0,0,0,0)` in server time) are each off by one to two hours around midnight; `landlords/page.tsx:50` prints a UTC calendar date. `stockholmDate` and `daysUntil` are correct; use them.

### Q9. Medium. Accessibility semantics

Fourteen `aria-label=""` on `nav`, `ul` and `ol` elements leave landmarks unnamed. `role="tab"` on links in the applications and duplicates pages promise arrow-key switching that does not exist. `dialog.tsx:52,65` hardcodes `id="dialog-title"` while pages mount several dialogs, so `aria-labelledby` can resolve to the wrong heading. `search-page.tsx:108` puts `aria-current` on a span. Fix: real landmark names, `nav` with `aria-current` instead of tabs, `useId()` in the dialog.

### Q10. Low. Duplication and dead code

`uniqueSlug` exists twice, tracked-field diffing three times, the feed-kind sniff regex twice, the delete-user-unless-member logic twice, and three shells hand-roll the same navigation. Nineteen `void x;` lines silence unused imports instead of removing them; four dead ternaries (`admin.ts:193` `? "private" : "private"` was clearly meant to differ). `localStorage` exported from `storage.ts` shadows the browser global. Several exports are unused. `docs/STATUS.md` still says 37 unit tests.

### Q11. Low. Type safety

25 `as never` casts, mostly erasing next-intl's typed pathnames on dynamic navigations, and message-key casts that turn missing keys into runtime failures. `admin.ts:34,160` cast `?status=` from the URL straight into an enum comparison, so `?status=foo` produces a Postgres error page. Fix: a typed href helper, constant key maps, and enum validation with a fallback.

### Q12. Low. i18n details

Two hand-built unit strings bypass `formatRent` and `formatSize`; three placeholders show Swedish in the English UI; the failure email always renders in Swedish regardless of landlord locale; a relative-time formatter is inlined outside `format.ts`.

## Tests worth adding

Nothing in the database, worker or action layer is unit-tested; the end-to-end suite exercises the UI but never calls a guarded action directly. In order of value:

1. `syncSource` against the docker database: create, update, remove only on success, keep everything when the fetch throws, flag an anomaly without removing.
2. `mergeListings` and `decideDuplicate`: sources move, loser marked, pending candidates closed, idempotent on repeat.
3. `requireStaff`: eight-hour cap, support calling a lead action, non-staff denied.
4. `requireLandlord` scoping: an owner of A calling `unpublishListing` on B's listing changes nothing.
5. `parseSearchParams`: per-field fallback and `toQuery` round trip.
6. `saveListing`: missing fields and an invalid image write nothing (would have caught Q1).
7. `org-number.ts`: Luhn, brf prefix, personal-number rejection.
8. `politeFetch`: robots disallow, per-host gap, timeout mapping, and after S1 the private-address rejection.

## Operations

No CI (`docs/TODO.md` B5 lists the five commands). No health endpoint for a load balancer. No structured logger; job outcomes are single `console.log` lines. Rate limiting and Better Auth rate limiting are in-process. `tsconfig.tsbuildinfo` is tracked and changes on every commit; add it to `.gitignore`. `scripts/start.sh` is macOS-only and `scripts/extract-design-copy.mjs` is a one-off that reads an ignored folder. `.env.example` is complete.

## What is done well

- Every portal mutation resolves its row with `and(eq(id), eq(landlordId, me.landlordId))`; image removal is scoped to the listing; staff and landlord membership are re-read from the database on every request rather than trusted from the session.
- Role checks are server-side in every action; the UI flags are cosmetic. Staff sessions are capped at eight hours on `createdAt`, which activity cannot extend.
- Invitation and reset tokens are random, hashed, expiring and single-use. Passwords are ten characters minimum, sign-in and reset responses are uniform, pending accounts reach only the pending page.
- All SQL is parameterised; the only `sql.raw` calls interpolate compile-time constants; ordering is a closed switch over an enum.
- Upload path handling is solid: key regex, `..` rejection, resolved-path prefix check, random file names, server-chosen extension.
- No `dangerouslySetInnerHTML`, every `target="_blank"` has `rel="noopener noreferrer"`, no open redirects, the image optimizer is locked to one host, portal and admin are fully noindex, no secrets in git.
- The worker never removes on failure, degrades with capped backoff, honours robots.txt with a cache, serialises per host with jitter, times out every fetch, and cannot pile up parallel crawls of one source. XML parsing has entity expansion limits and no external entities.
- Server and client boundaries are clean: no client file imports the database, queries, auth or zod at runtime.
- Public search parameters are parsed leniently with bounded enums and defaults, so junk input never errors the search page.
